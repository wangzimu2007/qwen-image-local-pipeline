## 六、几个"反转"结论

这几个月筛下来，最有价值的不是"能跑什么"，而是**一开始判断错、后来被推翻的东西**：

### 1. FlashVSR 一开始被判"不值得"，装对官方环境后反超

| 配置 | 处理分辨率上限 | 输出 | 耗时 |
|---|---|---|---|
| 原版 + 兜底注意力机制 | ~512×288 | 1024×512 | 43 秒 |
| **官方环境（plus 权重 + Triton 内核）** | **832×480** | **1664×896** | **76 秒** |

差别不在显卡，而在于**一个很容易漏装的依赖**（节点自带 Triton 内核）。
装上之后分辨率提升 3 倍、速度还更快。

### 2. "带音频的视频"以前被当成不可能

调研 MiniMax H3 时按体积和显存估算，结论是"24 GB 卡上不现实"（下载 45 GB、需重度 offload）。
实测相反：**44 GB 权重、960×540 只要 113 秒**，还能出 32 kHz 立体声。
关键是把 int8 剪枝 + nvfp4 编码器 + Turbo 8 步 LoRA 组合起来。

### 3. 加速 LoRA 不是越多步越好，也不是越少越好

| 配置 | 锐度 | 观感 |
|---|---|---|
| 8 步 + 加速 LoRA | 77 | 皮肤塑料、发丝糊 |
| **12 步 + 加速 LoRA** | **98** | 毛孔纹理都在 |
| 25 步 无加速 LoRA | 83 | 真实但粗糙 |

**加速 LoRA 在 8 步会把高频细节抹掉**；12 步才是甜点。

### 4. 风格 LoRA 锐度下降 ≠ 缺陷

- **风格型 LoRA**（朦胧/胶片）：锐度下降**就是要的效果**，调权重即可
- **加速型 LoRA**（turbo/DMD）：锐度下降是**步数不够**，要加步数

同一个指标（锐度），两种 LoRA 要作相反解读 —— 这是最容易误判的地方。

### 5. int8 视频 VAE 会静默产出全黑

H3 用 `minimax_h3_video_vae_int8_convrot` 时：**能加载、能跑完、音频正常、画面全黑**。
不看画面只看"成功"就会误以为通过。必须用 **fp16 版**。
验收方法：抽帧算亮度方差，`std < 1` 就是解码坏了。

## 七、踩坑精选（10 条）

| # | 现象 | 原因 | 对策 |
|---|---|---|---|
| 1 | 中文脚本报一堆"意外的标记"语法错误 | UTF-8 缺 BOM，PS 5.1 按 GBK 读 | 所有中文 `.ps1` 必须带 BOM |
| 2 | `value_not_in_list` | 模型名/LoRA 名不在下拉框；或端口上是错误引擎 | 查 `/object_info/UNETLoader` 的模型列表 |
| 3 | 画面全黑但音频正常 | 视频 VAE 用了 int8 量化版 | 换 fp16 版；抽帧验亮度 |
| 4 | 1080p 超分解码阶段爆显存 | 没开 VAE 分块 | 开 `--vae_decode_tiled` |
| 5 | 视频帧数不生效 / 报错 | 帧数必须 **4n+1**（Wan）/ **17k+5**（H3） | 让脚本自动算 |
| 6 | 中文路径读图失败 | OpenCV/PyAV 的编码问题 | 先复制到英文临时路径 |
| 7 | 提交阶段 400 直接崩 | 没包 try/catch | 把 4xx 当"这次失败"进入降级 |
| 8 | 两套快照互相覆盖 | 两个工具各写一个状态文件 | 一方独占，另一方传 `-KeepChatBackend/-NoRestore` |
| 9 | 恢复调用插不进去 | 结尾是 `if (...) { exit 0 }` 单行，多行正则漏匹配 | 恢复必须是顶层独立一行；**跑真测试验残留** |
| 10 | `git push` 被拒 | 本地与远端历史分叉 / 旧标签冲突 | `reset --mixed origin/main` 再提交；标签单独推 |
