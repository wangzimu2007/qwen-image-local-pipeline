# 作业队列：让本地聊天模型安全地调用出图

## 问题

本地聊天模型（Strata 8080 / Ollama 11434）占着 15~22 GB 显存，出图脚本为腾显存会把**正在服务你的
聊天模型**卸载掉 → 对话立刻断线（`TRANSPORT Connection error`），而且脚本末尾的"恢复模型"那一步
没人执行（因为执行者已经下线）。

**本质**：卸载动作不能由"被卸载者"自己执行。

## 方案：作业队列 + 独立守护

```
本地聊天模型 ──提交──▶ .jobs\pending\<id>.json
     │                        │
     │（不卸载自己）           ▼
     │                  作业守护（独立进程，开机自启）
     │                  ① 快照聊天后端（Strata 变体 / Ollama 模型）
     │                  ② 卸载 → 等显存
     │                  ③ 跑目标脚本（Z画图 / 编辑 / H3 …）
     │                  ④ 关闭 ComfyUI 引擎
     │                  ⑤ 恢复聊天后端
     │                  ⑥ 结果写 .jobs\done\<id>.json
     ▼                        │
  对话不断线 ◀────────────────┘
```

## 两个脚本

| 脚本 | 谁调 | 作用 |
|---|---|---|
| `submit-job.ps1`（本地 `提交作业.ps1`）| **聊天模型** | 显存够 → 同步出图（带 `-KeepChatBackend`，不卸载）；不够 → 写队列立即返回 |
| `job-worker.ps1`（本地 `作业守护.ps1`）| 用户/开机自启 | 消费队列：快照→卸载→出图→关引擎→恢复→写结果 |

## 用法（模型侧）

```powershell
提交作业.ps1 -Task zimage -Prompt "海边灯塔，黄昏"
提交作业.ps1 -Task edit -Image x.png -Prompt "把外套换成红色"
提交作业.ps1 -Task krea2 -Prompt "..." -Extra "Lora=aoi_haru:0.9"
提交作业.ps1 -Task zimage -Prompt "..." -Wait     # 排队后等结果
提交作业.ps1 -List                                # 任务清单 + 显存需求
提交作业.ps1 -Status                              # 队列状态
```

任务 → 显存需求：`zimage` 14000 / `moss` 15000 / `t2i` 16000 / `krea2` 19000 / `pixeldit` 11000 /
`edit` 21000 / `inpaint` 14000 / `pid` 21000 / `upscale` 16000 / `h3` 22000 / `i2v` 17000（MiB）。

## 硬防护（防自杀闸门）

`_vram.ps1` 里新增：

```
Get-DshActiveModel()          → 读 DSH 默认模型（provider/model）
Test-IsDshActiveBackend($b)   → 该后端是否正在服务当前对话
```

`Start-VramPrep` 在卸载前判断：**如果目标是 DSH 当前默认模型，且 `PIPE_ALLOW_SELF_UNLOAD` 不是 `1`
→ 抛出错误拒绝执行**。守护进程自己设置该环境变量，所以只有它能合法卸载。

于是：本地模型就算误调 `Z画图.ps1`，也只会得到一条清楚的中文报错，**不会断线**。

## 实测（RTX 5090 Laptop 24 GB）

| 步骤 | 结果 |
|---|---|
| 提交时可用显存 | 0.9 GB（Strata 占着 22.5 GB）|
| 判定 | 不足 13.7 GB → 排队，**聊天模型未动** |
| 守护执行 | 卸载 Strata → Z-Image 8 步出图 → 关引擎 → 恢复 Strata |
| 总耗时 | **144.9 秒**（其中恢复 Strata 约 60 秒）|
| 成品 | `qwen-0114-zimg-20261025-170936.png` |
| 恢复校验 | 8080 回来了，8188 已关 ✅ |

## 参数兼容坑

不同脚本参数不一致（`Z画图.ps1` 没有 `-NoPause`），守护进程用 AST 解析目标脚本来**只传它支持的开关**：

```powershell
Get-ScriptParamSet $path     # 读 param 块
Add-SupportedSwitch $list $set 'NoPause'
```

## 运维

- 启动：桌面「作业守护 - 启动」；开机自启已加入启动文件夹
- 停止：桌面「作业守护 - 停止」（队列保留）
- 查看：桌面「作业状态 - 查看」
- 日志：`.jobs\守护.log`；单作业输出 `.jobs\running\<id>.log`
- 单实例：`.jobs\守护.pid`
## 批量模式（v0.6.1）

守护进程**按批次处理**：一次 `Start-VramPrep`（卸载聊天模型）→ 跑完队列里所有作业 → 批末一次性
`关ComfyUI` + `Restore-VramPrep`。

| 场景 | 旧（逐个处理）| 新（批量）|
|---|---|---|
| 2 个作业 | 2 次卸载 + 2 次恢复 ≈ 2×(60+60)s | **1 次卸载 + 1 次恢复** |
| 实测 | — | 2 个作业共 **180 秒**（出图 67.6 + 85.5 秒） |

日志会打印 `本批 N 个作业，一次性卸载` 与批末恢复。

## 已修的两个 bug（v0.6.1）

| bug | 现象 | 原因 / 修复 |
|---|---|---|
| **参数拼接** | `找不到与参数名称"Lora xxx.safetensors"匹配的参数` | PowerShell 里 `@('-' + $name, $value)` 会拼成**一个字符串**；改成两次 `+=` |
| **批内重复卸载/恢复** | 排 3 个作业要花 6~7 分钟 | 引入批量模式，一次卸载/恢复 |
| **running 目录残留** | 失败作业的 log 留在 `running/` | 作业结束把 log 移到 `done/` |
## Strata 的资源画像（实测，2026-10-25）

Strata **不是只占显存**，它是三层占用——这决定了卸载/恢复的真实代价：

| 层 | 占用 | 卸载后变化 |
|---|---|---|
| **显存** | `strata.exe` 20.1 GB + `strata-vision.exe` 1.3 GB = **21.4 GB** | 释放到 22.5 GB 可用 |
| **物理内存** | 让可用物理内存掉到 **4.5 GB / 63.4 GB** | 释放到 **54.5 GB 可用**（腾出 50 GB）|
| **页面文件** | 已用 **92.2 GB** | 降到 **19.4 GB** |
| **磁盘** | `D:\Strata-data` 共 205.8 GB（主模型分片 51 + 27 GB、ple-fp8 47.7 GB）| 恢复时重新读入 |

**阶段计时（3 作业一批，实测）**：

| 阶段 | 耗时 |
|---|---|
| 卸载（停 Strata + 释放显存/内存）| **18.1 秒** |
| 出图 ×3 | 63.2 / 78.5 / 78.6 秒 |
| 恢复（启动 + 端口就绪 + 推理探针）| **40.6 秒** |
| **整批总耗时** | **284 秒** |

**结论**：真正的 bug 不是"内存/磁盘占用"，而是三个软件缺陷（见下）；
内存压力只影响"恢复慢"，批量模式已经把恢复次数压到 1 次。

## 已修的三个 bug

| # | bug | 现象 | 根因 / 修复 |
|---|---|---|---|
| 1 | **参数拼接** | `找不到与参数名称"Lora xxx"` | PowerShell `@('-' + $a, $b)` 拼成一个字符串 → 改两次 `+=` |
| 2 | **作业 ID 撞车** | 同秒提交 2 个 → 只跑 1 个 | ID 只有秒级精度 → 加毫秒 + 随机后缀 + 冲突检测 |
| 3 | **批内重复卸载/恢复** | N 个作业 = N×(卸载+恢复) | 批量模式：一次卸载、批末一次恢复 |

## 新增的观测与保护

- **内存快照**：批前 / 卸载后 / 恢复后各记一次「物理可用 + 页面文件」，写进日志
- **恢复探针**：恢复 Strata 后不止等 `/v1/models`，再发一次 `max_tokens=1` 的 chat 请求，
  确认真的能推理（失败重试 1 次）——避免"端口通了但模型没加载完"导致的断线
- **阶段计时**：卸载 / 每个作业 / 恢复 / 整批耗时全部落日志

## 画图任务结束后自动拉回 Strata（v0.6.3）

作业守护批末恢复后写标记 `.jobs\strata-wanted.json`；
`watchdog.ps1` 每 30 秒的 `Invoke-StrataKeeper` 据此检查：**队列为空 + 15 分钟窗口内 + 8080 不在** → 启动 Strata。

实测：手动停掉 Strata 后，watchdog 单次检查 **39 秒内拉回**；有作业时绝不触发（避免抢显存）。

为什么不做成"无条件常驻"：出图任务必须独占显存，常驻拉起会和任务互抢，双双变慢。
## 两个必须知道的坑（v0.6.3 实测）

### 1. 自动审查 + 本地模型会互相打架

本地模型会话开着「自动审查」时，每个工具调用前都要审查模型先过一遍，而审查模型就是同一个本地后端。
作业队列一开始执行就会卸载 Strata →

```
Auto review of tool "pwsh" failed; its body was not executed:
auto-review: reviewer ended with error TRANSPORT: Connect…
```

工具体**根本不会执行**。对策：本地模型会话关掉自动审查；**提交排队作业后立即结束本轮**，
不要在同一轮继续调工具、也不要用 `-Wait`。

### 2. 成品标签不统一

不同脚本打印的标签不一样：`成品：`（Z画图/PiD）、`编辑完成：`（编辑.ps1）、`超分完成：` 等。
守护的解析已放宽为 `成品|编辑完成|超分完成|视频完成|输出文件` + 后缀白名单，
否则会出现"图已生成但被判 failed"。

### 3. 任务参数不匹配要秒拒绝

`-Task krea2 -Image x` 会失败（Krea2 是纯文生图），但在以前是**先卸载后端 23 秒 + 恢复 45 秒**才发现。
现在 `submit-job.ps1` 提交前用 AST 读目标脚本的 param 块校验，**0.28 秒**拒绝并给替代方案。
## 状态查看（v0.6.4）

`scripts/status.ps1` 一条命令判断四种状态：

| 条件 | 状态 |
|---|---|
| 队列 running/pending > 0 | **出图中** |
| `.jobs\guardian.lock` 存在 | **恢复中**（约 45~70 秒）|
| 8080 + `/v1/models` 通 | **就绪** |
| strata 进程在但没答 | **启动中**（40~90 秒）|
| 都不是 | **离线** |

```powershell
status.ps1          # 一次性
status.ps1 -Watch   # 每 3 秒刷新直到就绪
status.ps1 -Json    # 机器可读
```

实测切换：`20:25:19 出图中 → 20:26:51 恢复中 → 20:27:45 就绪`。

**顺带修的并发 bug**：守护恢复 Strata 时，watchdog 的 Keeper 也在拉 → 两边各跑 `launch --stop`
互相打断（日志出现 KeyboardInterrupt，残留半死进程挡住后续启动）。
修法：守护批处理期间写 `guardian.lock`，Keeper 见锁让路；启动前清理残留 strata 进程。

## 一次提交多张（批量提交，v0.6.6）

本地模型会话里，**一张一张提交会因为卸载后端而断线**。现在支持一次提交多张：

```powershell
提交作业.ps1 -Task zimage -Prompt "雪山日出" -Count 3 -Seeds "11,22,33"
```

- `-Count N`：一次写 N 个作业（上限 16）
- `-Seeds "11,22,33"`：每张独立种子；不给则各自随机
- 守护有 **4 秒收集窗口**：把同时到达的作业合并成一批 → **只卸载/恢复一次**

**实测（3 张 zimage）**：

| 阶段 | 耗时 |
|---|---|
| 卸载 | 22.6 秒 |
| 出图 ×3 | 68 + 95 + 87 秒 |
| 恢复 | 44.9 秒 |
| **整批** | **322.7 秒** |

对比逐张提交：3×(22.6+80+44.9) ≈ **440 秒** → 省约 120 秒。

### 这轮修掉的三个 bug

| bug | 现象 | 根因 |
|---|---|---|
| **参数重复** | 作业 0 秒失败 `-NoPause 被指定多次` | 守护自动加开关，未检查作业参数里已有 |
| **变量名撞车** | 批处理跑完第 1 张就跳出，剩两张卡 pending | `foreach ($sw in 'KeepChatBackend',...)` 把计时器 `$sw` 覆盖成字符串 → `$sw.Stop()` 抛异常 |
| **批被拆开** | 3 张拆成 3 批，各卸载一次 | 守护两次扫描之间没有等待 → 加 4 秒收集窗口 |

另外：单实例改用**文件独占锁**（扫进程会把自己/残留算成"已有实例"）；单作业异常不再拖垮整批。

## 阻塞等待（-Wait）与自动续跑（v0.7.1）

本地模型会话断线的根因是：作业批把聊天模型卸载了，模型无法再发起下一轮推理。
解法是**让工具调用原地阻塞到后端恢复**：

```powershell
提交作业.ps1 -Task zimage -Prompt "..." -Wait
```

`-Wait` 返回前必须四个条件全部成立：

| 条件 | 文件/探测 |
|---|---|
| 作业完成 | `.jobs/done/<id>.json` |
| 守护不忙 | `.jobs/guardian.lock` 不存在 |
| 批末恢复完成 | `.jobs/last-batch.json`（`by=guardian`，时间戳晚于提交）|
| 聊天后端能应答 | `Get-LocalBackends -Role chat` 中 `serving=true` |

守护写标记的顺序（关键）：

```
作业逐个完成 → 写 done/<id>.json
  → 批末恢复后端（Restore-VramPrep）
  → 写 last-batch.json（by=guardian）
  → 删除 guardian.lock
```

因此"批末标记 + 锁释放"同时出现，才代表后端真的回来了。

批量建议：一次 `-Wait` ≤2 张；3 张实测 322.7 秒，可能超过工具调用超时。超过就拆成多次调用，
每批之间后端都已恢复，会话不断。

云端会话（DSH 默认不是本地 chat）会自动跳过"等后端"条件。

### 实测（2026-10-26 18:00）

| 测试 | 结果 | 总耗时 | 说明 |
|---|---|---|---|
| 单张 + `-Wait` | 通过 | 53.5 s | 队列模式，返回时后端就绪 |
| 一次 2 张 + `-Wait` | 通过 | 79.0 s | 「本批 2 个作业」，只恢复一次（6.3 s）|
| 两条同时提交 | 通过 | 64.3 s | 合并成同一批 |
| 批中追加 | 通过 | 144.6 s | 批大小 [1,1]，不打断 |
| 显存充足时并发 | 通过 | — | 一条 sync、一条自动转 queue（`sync.lock` 互斥）|

单张出图 23.2 s；模型恢复 6.3 s（真加载 20.6 GB）。
